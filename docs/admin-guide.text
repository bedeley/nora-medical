## Overview
- What it is: A back-office portal for operations, accounting, HR, and settings.
- How to use: Start at /admin/dashboard, then use the top nav or Admin menu.
- Related: Most pages are role-gated; STAFF/ACCOUNTANT see limited options.

## Access & Security
- Pages: /admin/mfa, /unauthorized
- What it is: Admin 2FA setup and access control feedback.
- How to use: Enable 2FA on first admin login; use TOTP codes to access admin routes.
- Related: Admin sessions expire and are enforced in middleware.
- Role gates: Admin-only actions include purchase creation/receiving, returns/refunds, supplier payments, and journal approvals.
- Users & roles: Manage staff roles in /admin/users (role changes require NEXT_PUBLIC_ADMIN_ROLE_MANAGEMENT_ENABLED=1). Use “Invite employee” to send a 24-hour invite link with verification code via email ? SMS ? WhatsApp fallback.

## Dashboard & Recent Activity
- Pages: /admin/dashboard, /admin/recent
- What it is: KPIs and latest operational activity.
- How to use: Monitor sales, payments, inventory alerts, and trends.
- KPI interpretation:
  - `Billed order total` is tax-inclusive.
  - `Gross sales` is pre-tax sales value.
  - `Tax collected` is shown separately.
  - `Discounts` is shown separately and reduces net sales.
  - Reconciliation card explains: `Billed = Collected + Outstanding`, and `Billed = Gross + Tax - Discounts`.
- Related: Uses live order/payment/expense data; can switch to ledger reporting.

## Products & Catalog
- Pages: /admin/products, /admin/purchases, /admin/movements
- What it is: Catalog maintenance and stock movement tracking.
- How to use: Add/edit products, upload images, archive obsolete items, and record purchases.
- Add product (initial stock vs order):
  - Receive now checked: creates a received purchase, posts inventory + AP, and logs an inventory movement.
  - Receive now unchecked: creates an ordered purchase only; stock stays 0 until received later.
  - Pay now: records a supplier payment and posts AP to Cash/Bank.
  - Add Product modal uses inline field validation (supplier, lot/batch, expiry date, and payment mode) so missing fields are shown directly beside the input.
  - Purchase form uses inline field validation for required inputs (product, quantity, unit cost, supplier, and payment mode when Pay now is checked).
  - Regulated/lot-history SKUs enforce lot code at receipt; expiry date is enforced when expiry tracking applies.
- Cleanup behavior:
  - Deleted products are hidden from product pickers by default.
  - If a deleted product has an unreceived/no-history purchase draft (pending/approved/ordered/cancelled with no movements/payments/lots), that purchase is soft-removed from operational pages.
- Related: Product stock drives inventory alerts and order fulfillment.

## Suppliers
- Page: /admin/suppliers
- What it is: Supplier directory with lead times, status, and purchasing defaults.
- How to use: Add suppliers, set lead time (avg/min/max), status (active/on hold/inactive), and defaults (MOQ/pack size).
- Aging hub drill-through:
  - `Open suppliers` from Aging Hub opens this page sorted by supplier name.
  - A subtle `Applied from Aging Hub` badge appears when opened with that context.
- Archive/Restore: Use Archive to hide a supplier without losing history; toggle "Show archived suppliers" to restore.
- Lead time validation: Min must be <= max; the form will block invalid ranges.
- Related: Supplier status and lead time feed inventory planning and alerting.

## Suppliers — Performance
- Page: /admin/suppliers/performance
- What it is: Supplier scorecard tracking fill rate, on-time delivery, lead time, and spend.
- How to use: Review the breakdown table; click a supplier to open the filtered Suppliers list.
- Notes: Supplier is required when creating purchases.
- Related: Use this when deciding preferred vendors or resolving supplier-driven stock issues.

## Orders & Receipts
- Pages: /admin/orders, /admin/orders/new, /admin/orders/[id], /admin/orders/[id]/receipt
- What it is: Order lifecycle management and admin receipt handling.
- How to use:
  1) Create order (full or partial payment).
     - Flow is optimized for operations: select customer -> add order lines -> finalize payment/delivery.
     - If `Delivery Status = Partially Delivered`, enter delivered quantity for each line item before saving.
     - Upfront payment fields are collapsed by default; click `Enable Payment` only when collecting payment at order creation.
     - Upfront payment mode uses explicit placeholder selection (no default payment method).
     - If upfront payment is enabled, amount and required reference fields are validated inline before create.
     - Walk-in/unregistered customers are excluded from `/admin/orders/new` customer list; use OTC for walk-ins.
  2) Record remaining payments from order page (cash/transfer/momo).
  3) Mark delivery status.
  4) Process returns from item row.
  5) Validate payment summary line:
     - Ledger total
     - Less non-ledger return credits
     - Net paid (must match Amount Paid)
  6) If you see a protracted pending provider MoMo warning on the order:
     - Use `Cancel pending MoMo request(s)` if customer wants another payment method.
     - Record alternate payment (cash/transfer/manual MoMo) only once.
     - If provider later returns success after cancel, keep order unchanged and resolve on MoMo page as store credit.
- Expected:
  - Partial payment -> `PARTIALLY_PAID`
  - Full payment -> `PAID`
  - Discounts are admin-only and must include a reason.
  - `/admin/orders` list shows discount under the order total when applied.
  - Order receipt and customer receipt show: Subtotal, Tax, Discount, Invoice total.
  - Receipt layout is compact and operational: customer/status in header cards, item grid, delivery summary, and right-aligned financial summary.
  - Partially delivered status requires per-line delivered quantities; fully delivered lines should use `Delivered`.
  - Return credits reduce net paid correctly without false mismatch warnings.
  - Provider MoMo pending does not count as paid until confirmed success.
  - If page is opened with `outstandingOnly=1`, the header shows `Collections mode: Outstanding only`.
  - Use `Show all` in the badge to return to normal full-order listing.
- Related: Orders feed accounting, inventory movements, and customer balances.

## Orders — OTC Sales
- Page: /admin/orders/otc
- What it is: One-screen walk-in OTC checkout with shift lock control.
- How to use:
  1) Open shift first (required).
  2) Enter walk-in name (required by default), or use anonymous exception with reason.
  3) Add items and choose payment method.
  4) Review pre-submit summary strip (`Payment type`, `Will create status`, `Will mark delivery as`).
  5) Complete sale from confirmation modal, then print receipt or open order details.
- MoMo handling:
  - `Create Sale + Request MoMo` for in-app live request flow.
  - `Record Existing External Payment` for already-paid external transactions.
- Notes:
  - Walk-in name is required by default.
  - Anonymous sale is allowed only as an exception and requires a reason.
  - Anonymous OTC sales must be paid in full (no partial/unpaid balance allowed).
  - Named walk-in OTC sales can be full, partial, or unpaid.
  - Customer match supports registered users and prior walk-in history.
  - Non-cash reference is required only for `Record Existing External Payment`.
  - Live MoMo requires a valid 10-digit phone number; submit is blocked by inline validation if invalid.
  - Payment reference field appears only when required by selected mode/capture flow.
  - Delivery defaults to `Delivered`, with a checkbox to create as `Not delivered` when goods should be held.
  - For live MoMo requests, keep goods on hold until payment status is confirmed successful.
  - Admin can apply discount amount; discount reason is required and captured in audit metadata.
  - Discount auto-adjusts `Amount Paid Now` to net payable for paid flows; credit/unpaid flows are not auto-paid.
  - Unsaved OTC drafts auto-save for 3 minutes and can be restored.
  - Keyboard shortcuts: `Alt+I` add item, `Alt+S` submit.
  - Submit button is guarded against duplicate clicks on slow networks.
  - Returns for OTC orders are tracked in Returns/RMA and customer account credit.
- Related: OTC orders post to the journal when auto-post is enabled.

## OTC Shift Close
- Page: /admin/otc/shift-close
- What it is: End-of-day OTC reconciliation and lock control.
- How to use:
  1) Select day and refresh summary.
  2) Compare expected cash/bank totals with counted actuals.
  3) Use `Use Expected Amounts` for quick zero-variance close when counts match.
  4) Resolve unposted payment warnings (sync) before final close, or override with reason.
  5) Close shift and verify row in Recent Shift Closes.
- Lock behavior:
  - Before open: OTC sale creation blocked.
  - After close: OTC sale creation blocked for staff.
  - Admin can emergency-override after close with reason.
  - New day requires manual open (staff after 06:00 UTC, admin anytime).
- Related: Audit logs use `OTC_SHIFT_OPEN` and `OTC_SHIFT_CLOSE` with human-readable metadata.

## Payments — MoMo Settlement & Reconciliation
- Page: /admin/payments/momo
- What it is: Ghana-specific MoMo monitoring for provider requests, manual records, and reconciliation outcomes.
- How to use:
  - Use Status + Provider filters to isolate pending vs settled.
  - `Source` helps interpretation:
    - `Provider`: initiated from app and waiting/confirmed from provider callbacks.
    - `Manual`: recorded external payment; treated as settled from operations side.
  - `Ledger: Posted/Unposted` shows whether the journal entry exists for the payment.
  - The `Actions` column only appears when at least one visible row is actionable.
    - If all rows are view-only, the column is hidden.
  - For long-running pending provider requests:
    1) Open row and click `Cancel pending`.
    2) Collect alternate payment if needed (cash/transfer/manual MoMo).
    3) If provider later returns success, row becomes `late_success_after_cancel`.
    4) Click `Resolve to Credit` to move amount to customer store-credit liability.
- When to act:
  - Pending for long periods: cancel and use alternate payment flow (avoid duplicate collection).
  - Settled but Unposted: run Sync ledger in Accounting ? Data Integrity.
  - Late success after cancel: resolve to credit, then refund from customer account if cash return is needed.
- Note:
  - This page is operational control + monitoring.
  - Detailed ledger behavior for these events is documented under Accounting ? Posting Rules and Accounting ? Journal.
- Test-mode simulation (technical, not daily operations):
  - `Simulate Late Success` is hidden by default.
  - It appears only when test tools are enabled in non-production.
  - Use it only for QA/UAT to verify late-success-after-cancel handling.

## Inventory — Lots & Expiry
- Page: /admin/inventory-lots
- What it is: Batch/lot tracking with expiry dates for compliance and audits.
- How to use: Review lot balances and expiry windows; use FEFO Priority + Days left to plan picking.
- FEFO behavior: Lots expiring sooner are sold first.
- FEFO visuals: Priority labels use threshold bands (High 0-high threshold, Medium high+1-medium threshold, Low medium+1+, No expiry). Threshold days are configurable in app settings (`inventory.lots.fefo.thresholdDays.high`, `inventory.lots.fefo.thresholdDays.medium`).
- Traceability: Use `Trace` on any lot to view source purchase details and lot-level movement history, export adaptive CSV files (single combined export for 0-1 movement; separate summary/movements for 2+), and deep-link into Purchases or lot-filtered Movements.
- Movement navigation: Use `View all lot movements` from Trace to open all movements for the selected lot (not a single reason-only subset).
- Related: Lot details are captured on receive; batch code and expiry are required for lot-tracked items.

## Inventory — Stock Adjustments

- Posts: Creates inventory movement + journal entry to keep valuation aligned.
- Related: Movement details show the adjustment reason in the modal.

## Supplier + Inventory Enhancements
- Pages: /admin/suppliers, /admin/products, /admin/purchases, /admin/inventory-planning, /admin/dashboard
- What it is: A tighter loop between suppliers, purchasing, and planning (alternate suppliers, approvals, receipts, and alerts).
- How to use:
  1) Suppliers: Set lead time avg/min/max, default MOQ/pack size, and status.
  2) Products: Link alternate suppliers and mark a primary supplier in the Edit dialog.
  3) Purchases: Create purchase orders with expected arrival; large quantities are pending approval.
  4) Approvals: Admins approve pending purchases before receiving stock.
  5) Receiving: Use Receive to record partial/full receipts; on-order is reduced automatically.
- Alerts: Inventory alerts include low stock, supplier inactive, lead time missing, and demand spike.
- Related: Planning suggestions round to pack size and respect supplier lead time variability.
Step-by-step (enhanced workflow)
1) Suppliers setup
   - Add supplier name, status, lead time avg/min/max, and defaults (MOQ/pack size).
   - Example: “MedSupply Wholesale” · ACTIVE · lead time 14/10/21 · MOQ 50 · pack 10.
   - Example (cartons): If a carton has 12 units and MOQ is 2 cartons, set MOQ = 24 and pack size = 12.
   - Use ON_HOLD/INACTIVE to pause new orders; alerts will flag products tied to them.
2) Product linkage
   - Open a product and set the primary supplier in the main supplier selector.
   - Add alternates in the supplier links panel, with optional overrides for lead time/MOQ/pack size.
   - Use “Set as primary” if you switch vendors.
   - Example: Primary = MedSupply Wholesale (lead time 14), Alternate = HealthPro (lead time 21, MOQ 100).
3) Purchase creation (PO)
   - Create a purchase with supplier + expected arrival date.
   - Leave “Receive now” unchecked when it’s an order, not a delivery.
   - Large quantities go to PENDING_APPROVAL automatically.
   - Example: 500 units @ 12.50 from MedSupply, expected 2026-01-15 ? status PENDING_APPROVAL.
4) Approval (admin)
   - Approve PENDING_APPROVAL purchases from the Purchases table.
   - Once approved, the PO can be received.
   - Example: Admin approves PO-123; status moves to APPROVED.
5) Receiving (partial/full)
   - Click Receive and enter the quantity received (partial or full).
   - Stock, inventory movement, and accounting entry update on receipt.
   - Remaining on-order quantity stays in planning until fully received.
   - Example: Receive 200/500 ? status PARTIALLY_RECEIVED; on-order remains 300.
6) Alerts + Planning
   - Check Inventory Alerts for low stock, supplier inactive, lead time missing, and demand spikes.
   - Recompute Inventory Planning to refresh suggestions based on new receipts and demand.
   - Example: Demand spike shows 2.1 vs 1.3 avg/day; suggestion rounds to pack size 10.

## Inventory Planning
- Pages: /admin/inventory-planning, /admin/inventory-planning/[id], /admin/inventory-planning/reports
- What it is: Demand-driven planning using the last 60 days of sales, current stock, reserved stock, and on-order purchases.
- How to use: Recompute demand, review suggestions, tune reorder points/lead times only when needed.
- Related: Suggestions support purchasing decisions and reduce stockouts.
Inventory Planning — Overview
- Page: /admin/inventory-planning
- What it is: Main planning dashboard summarizing demand, available stock, effective planning values, and suggestions.
- How to use: Recompute demand; the system auto-derives reorder/safety stock, and manual settings override.
- Default reorder point: Sets the fallback reorder point used when demand history is zero.
- Per-product fallback: In the product detail page, you can override the fallback reorder point for zero-demand items.
- Auto recompute toggle (Daily/Weekly): This saves your preference. It only runs if a cron job calls the recompute endpoint.
- Cron setup (Vercel):
  1) Set `CRON_SECRET` in Vercel and your server env.
  2) Add a Cron Job targeting `https://your-domain.com/api/admin/inventory-planning/recompute`.
  3) Add header `Authorization: Bearer <CRON_SECRET>`.
  4) Schedule daily or weekly; the endpoint respects the toggle and last run time.
- Related: Uses 60-day demand snapshots and open suggestions.

Inventory Planning — Product Detail
- Page: /admin/inventory-planning/[id]
- What it is: Per-product planning settings and suggestion details.
- How to use: Review demand snapshot, adjust reorder point/safety stock/lead time, dismiss suggestions if needed.
- Related: Settings feed recompute logic for suggested quantities.
Step-by-step (product detail)
1) Open a product from /admin/inventory-planning.
2) Review the demand snapshot (period, units sold, average daily demand).
3) Check the restock suggestion; if none, the product is above reorder thresholds.
4) Update planning settings:
   - Reorder point, safety stock, lead time days, review period days, min order qty, target stock.
   - Default reorder (no demand): per-product fallback used when demand history is zero.
   - Approval threshold qty (optional): per-product cutoff for purchase approval.
   - Target stock: desired on-hand level after replenishment; when set, suggestions aim to reach this level.
5) Save planning settings.
6) Return to /admin/inventory-planning and click Recompute demand to refresh suggestions.

Inventory Planning — Reports

- What it is: Export center for restock suggestions.
- How to use: Download CSV and share with purchasing/suppliers.

## Accounting Portal Overview

- What it is: Main control center for chart of accounts, journal, reports, reconciliations, integrity checks, and posting rules.
- How to use:
  1) Start each day in Data Integrity (quick check).
  2) Use Journal for posting review and drill-down.
  3) Use Cash Reconciliation (operational mode) for end-of-day cash-up.

## Accounting — Accounts
- Page: /admin/accounting/accounts
- What it is: Chart of accounts (COA) used by auto-posting and reporting.
- Account code meanings (plain language):
  - 1000 Cash: physical cash on hand (till/office cash).
  - 1010 Bank: money in business bank/mobile money settlement bank account.
  - 1020 Cash in Transit: cash collected but not yet handed over/confirmed in treasury.
  - 1030 MoMo Clearing: pending MoMo provider receipts before final settlement.
  - 1040 Payment Gateway Clearing: online gateway receipts waiting for bank settlement.
  - 1100 Accounts Receivable: customer balances still owed to the business.
  - 1200 Inventory: stock value currently held.
  - 2000 Accounts Payable: supplier invoices still unpaid.
  - 2100 VAT Payable: VAT liability (output VAT less input VAT, by filing period).
  - 2200 Store Credit: customer credit liability available for future orders/refunds.
  - 2300 Accrued Expenses: expenses incurred but not yet paid/invoiced.
  - 2400 Payroll Payable: salaries/wages accrued but not yet paid.
  - 2500 Unearned Revenue / Customer Deposits: customer money received before delivery.
  - 3000 Owner's Equity: owner capital introduced into the business.
  - 4000 Sales Revenue: recognized sales income after delivery/invoicing rules.
  - 5000 Cost of Goods Sold: inventory cost recognized for items sold.
  - 6000 Operating Expenses: general operating costs not mapped to a specific expense account.
  - 6100 Payroll Expense: payroll cost recognized for the period.
  - 6200 Delivery & Logistics Expense: shipping/rider/freight operating costs.
  - 6300 Bank Charges & Fees: bank and payment processing charges.
  - 6400 Utilities Expense: electricity, water, internet, and similar utilities.
  - 6500 Rent Expense: rent/lease cost for premises.
  - 6600 Repairs & Maintenance: maintenance and repair costs.
  - 6700 Marketing Expense: advertising/promotion costs.
  - 6990 Cash Over/Short: variance account for cash count differences.
- Core protected system accounts:
  - 1000 Cash
  - 1010 Bank
  - 1020 Cash in Transit

## Accounting — Journal
- Page: /admin/accounting/journal
- What it is: Book of record for posted, draft, and void entries.
- Top-to-bottom walkthrough:
  1) Header and open period context:
     - Shows page title and current open fiscal period.
  2) Export/actions strip:
     - `Export CSV (filtered)`, `Export PDF (filtered)`, `Export audit pack`, `Export audit pack PDF`.
     - `Show manual entry` toggles manual entry forms.
  3) Journal policy summary card:
     - Shows effective journal policy currently in force:
       - recent-window days,
       - manual P&L allow/block state,
       - archive default months,
       - archive cron dry-run/live mode.
  4) Quick tour + draft queue strips:
     - Quick tour explains review flow and keyboard shortcuts.
     - Draft queue shows draft count, oldest draft age/memo, and `Approve oldest`.
  5) Scope summary row:
     - Shows current scope/status/source/archive and entry counts for active query.
  6) Primary filter row:
     - Search box (`Search memo/source`) is debounced and server-side.
     - Status and source selectors.
     - `Out-of-balance only`.
     - `Include archive`.

  7) Advanced filter panel:
     - Link/batch search, account text search, account dropdown, account drill chips.

     - Period/date controls.
     - Exception toggles: `Missing source ref`, `Large amount`, `Stale drafts 7d+`.

  8) Saved view + work mode controls:

  9) Archive controls and timeline:

  13) Table and row actions:

  14) Pagination and keyboard workflow:
      - `First`, `Prev`, `Next`, `Last`, and page `Go`.
      - Keyboard: `J/K`, `Shift+J/K`, `Enter`, `A`, `Home/End`, `G/Shift+G`.

- Summary behavior:
  - `Summary basis` selector controls how outstanding/reconciliation are presented:
    - `Operational exposure`: includes full operational open exposure.
    - `Ledger AP basis`: focuses on received AP outstanding.
  - Meaning and use:
    - `Operational exposure` answers: “What supplier obligations are still operationally open right now?”
      - Includes open ordered/not-yet-received exposure plus received/unpaid exposure within current page scope.
      - Use for procurement execution, supplier follow-up, and expected-date discipline.
    - `Ledger AP basis` answers: “What amount is currently represented as AP liability in accounting view?”
      - Anchors reconciliation toward received AP positioning.
      - Use for accounting controls, AP review, and period-close checks.
  - Why compare both:
    - Comparison identifies timing/process gaps between operations and accounting treatment.
    - Small temporary differences can occur during normal posting windows.
    - Persistent differences indicate action is needed.
  - Recommended cadence:
    - Daily during active operations; minimum weekly review.
    - At period close, review and resolve deviations before final sign-off.
  - Deviation triage (practical order):
    - Confirm filters/scope first (supplier, month, status, strict date toggle).
    - Check unposted/pending approvals and recent receives/payments.
    - Verify expected-date/state transitions on open purchases.
    - Reconcile credits/refunds and supplier-specific credit carryover.
    - Re-run integrity/health checks if mismatch persists.
  - Deviation threshold alerts:
    - Configure absolute and percent thresholds on the page.
    - Warning/critical badges appear when basis delta exceeds configured guardrails.
  - Difference drilldown:
    - Use `Why this difference?` to view quick contributors:
      - ordered not received exposure
      - pending purchase/payment approvals
      - credits/refunds
      - strict-date scope state
  - "Pending payment approvals" reflects supplier payment requests awaiting approval.
  - "Pending purchase approvals" reflects purchase orders awaiting approval (separate from payment approvals).
  - Verify reconciliation line:
    - `Total amount - Paid - Supplier credits + Refunds = Reconciliation net payable` (based on selected summary basis).
  - Desktop includes sticky mini-summary while scrolling (`Open exposure`, `Received AP`, active filter).
  - Supplier-specific aging mini-chart shows bucket concentration by selected supplier.
- Pending approval behavior:
  - "Pending approval" totals include only payments that are still unapproved.
  - Once approved, they no longer count as pending and are posted as paid.
- Posting logic:
  - Purchase receive: Dr Inventory, Cr AP.
  - Supplier payment: Dr AP, Cr Cash/Bank.
  - Supplier return/refund paths reverse AP/inventory appropriately.
- Exports and communication:
  - "Export current view (CSV/PDF)" exports detail rows for current filters/scope.
  - "Export summary (CSV/PDF)" exports totals and reconciliation snapshot.
  - "Export email summary (TXT)" downloads plain text template for manual email.
  - "Send summary email" opens a modal (To/CC/Subject/Message) and sends current summary directly from app (Admin permission required).

    - for full unattended automation, wire cron/job runner to call supplier summary email endpoint.
  - AP Aging cross-link:

### Single Assignment Flow (Admin)

  2) Choose dispatcher from dropdown (system user) or use manual rider name/phone.
  3) Choose assignment scope:

     - Partial: set item-level assigned quantities in manifest.
  4) Save assignment.

  - Assignment metadata is visible on the order row and used by dispatcher app.

### Bulk Assignment Flow (Admin)
- Use when assigning multiple orders together:
  1) Select rows with checkboxes.
  2) Fill dispatcher/manual rider fields.
  3) Choose either:

     - Leave unchecked to open item-level bulk editor.

  - Partial assignment uses quantities (not percentages).

### Delivery Status Update (Admin)
- `Actions` -> `Update status` supports:
  - Pending, Assigned, Out for delivery, Failed attempt, Rescheduled, Partially delivered, Delivered.
- Rules:
  - `Partially delivered` requires item-level delivered quantities.
  - `Delivered` can capture POD details (recipient name/phone, note, image URL/upload).
  - POD warning should only appear for dispatch-managed deliveries where POD is required.
  - Orders updated as delivered outside dispatch context (e.g., order page pickup) should not trigger false POD missing follow-up.

### Failed/Rescheduled Custody Handover
- Problem solved:
  - Failed/rescheduled trips can still be physically with the dispatcher.
- Implemented behavior:
  1) Dispatcher marks `FAILED_ATTEMPT` or `RESCHEDULED`.
  2) System flags `return pending handover`.
  3) Order remains visible to that dispatcher until handover is confirmed.
  4) Admin uses `Confirm return received` in Dispatch actions.
  5) System clears assignment after confirmation; rider no longer appears as current assignment on that order.
- Reassignment policy:
  - Reassign is blocked while return handover is pending.
  - Unassign is also blocked while return handover is pending.
  - Confirm return first, then reassign.

### Collection Claims (Dispatcher -> Admin Confirm)
- Recommended control flow (implemented):
  1) Dispatcher marks order delivered.
  2) Dispatcher records collection claim (amount/method/reference/note) when applicable.
  3) Admin confirms claim from Dispatch board (`Confirm + Post Payment`).
  4) Only on admin confirmation does official payment ledger/journal posting occur.
- Why:
  - Prevents unverified field collections from posting directly to finance.
  - Maintains separation between operational claim and accounting confirmation.

### Unassign / Reassign
- `Actions` menu includes unassign with modal confirmation and reason.
- Use when rider unavailable, wrong assignment, or reroute is needed.
- Reassign by running assign flow again.

### Dispatcher App (`/dispatch/my-deliveries`)
- What it shows:
  - Active assignments (actionable).
  - Completed today (read-only summary).
  - Delivery history (collapsible cards for better long-list usability).
- Expected behavior:
  - Dispatcher updates only assigned manifest for that trip.
  - Dispatcher can capture POD on delivered updates:
    - recipient name/phone,
    - delivery note,
    - proof image URL, or direct image upload from phone camera/gallery.
  - Completed fully-settled items fall off active list.
  - Failed/rescheduled assignments can be hidden from active queue and reassigned by admin.
  - Historical deliveries remain searchable in history section.

### Delivery Scope Model (Important)
- Assignment scope is set by admin, not dispatcher:
  - Dispatcher delivers what was assigned on manifest.
